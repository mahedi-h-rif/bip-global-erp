SoudaCore ERP: security

How the BIP Gulf ERP is protected, from the server firewall down to each API call, and the exact commands to check each protection yourself. Production is https://erp.bipgulf.com; UAT is http://2.24.60.124:8088. Both run on one Ubuntu 24.04 server.

Active already running   Added in the latest change, live after the next deploy   Recommended not yet done

Overview

A request passes through several independent layers. If one layer fails, the next one still stops an attacker.

1
Server firewall only SSH, 80, 443, 8088 and 8089 are open. Web connections are rate-limited per IP, and fail2ban bans SSH password guessers.
2
Caddy front door the only published container. It provides HTTPS with automatic certificates and HSTS, and records each visitor's real IP.
3
API rate limits 600 requests a minute and 10 sign-in attempts a minute per visitor by default (admins can change both in Company settings). A single account is locked for 15 minutes after 5 wrong passwords.
4
Authentication BCrypt passwords, signed session cookie (HttpOnly, Secure, SameSite=Strict), CSRF token on every change.
5
Authorization roles, per-feature permissions, branch logins limited to their own records.
6
Data database never exposed, ZATCA keys encrypted (AES-256-GCM), secrets outside git, nightly backups.

Server firewall

Set up by deploy/server-firewall.sh. Every deploy re-applies it, and the same script can be run on its own.

ProtectionWhat it doesStatus
ufw default denyBlocks every incoming connection except SSH (22), HTTP (80), HTTPS (443) and the portal ports 8088 (UAT) and 8089 (production).Active
Database not publishedPostgreSQL has no public port. Only the API containers reach it, on Docker's internal network.Active
API not publishedThe Spring API (8080) is internal only. Browsers reach it through the portal.Active
Only Caddy publishedThe portal containers are no longer published directly. Caddy serves 80, 443, 8088 and 8089.Added
Per-IP connection limitsDocker-published ports bypass ufw, so a DOCKER-USER rule limits each source IP to 50 new connections a second (burst 200) and 300 open at once. Floods are dropped before they reach Caddy. A systemd unit (bip-docker-limits) restores the rule after a reboot.Added
fail2ban for SSHBans an IP for 1 hour after 5 failed SSH logins within 10 minutes. The old jail watched sshd.service, but Ubuntu 24.04 calls the service ssh.service, so it never banned anyone. It now watches the right service.Fixed
How to checkSign in to the server (ssh root@2.24.60.124) and run:
# 1. Firewall rules: expect "Status: active" and 22, 80, 443, 8088, 8089 ALLOW
ufw status verbose

# 2. Only these ports are listening publicly (22, 80, 443, 8088, 8089). Nothing on 5432 or 8080.
ss -tlnp | grep -v 127.0.0

# 3. Per-IP connection limits for Docker ports: expect a jump to BIP-LIMITS, a connlimit and a hashlimit rule
iptables -S DOCKER-USER
iptables -S BIP-LIMITS
systemctl status bip-docker-limits --no-pager

# 4. fail2ban is watching SSH: "Total failed" grows as bots try passwords; "Banned IP list" shows who is blocked
fail2ban-client status sshd

# 5. Containers: only caddy has 0.0.0.0 port mappings
docker ps --format 'table {{.Names}}\t{{.Ports}}'

From your own computer, the database and the API must not answer:

nc -vz -w 3 2.24.60.124 5432   # expect: timed out / refused
nc -vz -w 3 2.24.60.124 8080   # expect: timed out / refused
nmap -Pn 2.24.60.124           # expect only 22, 80, 443, 8088, 8089 open

Rate limiting

Limits at three levels, so a single visitor can't overload the system or keep guessing passwords.

LevelLimitWhen exceededStatus
Network (iptables)50 new connections/second per IP (burst 200), 300 open connections per IPExtra connections are droppedAdded
SSH (fail2ban)5 failed sign-ins within 10 minutes per IPThat IP is banned for 1 hourFixed
API, all calls600 requests/minute per visitor IP (changeable in Settings → Company)429 Too Many Requests with Retry-AfterAdded
API, sign-in10 attempts/minute per visitor IP (changeable in Settings → Company)429 with Retry-AfterAdded
Account lockout5 wrong passwords for one emailThat email is locked for 15 minutes (429 locked)Active

The API identifies each visitor by IP. Caddy discards any X-Forwarded-For header a client sends and writes the real address, so the limit can't be dodged with a fake header. An admin can change both limits under Settings → Company → API rate limits: requests per minute (60 to 100000) and sign-in attempts per minute (3 to 1000). 0 means no limit, and an empty field means the server default (600 and 10). A new value takes effect at once, and every change is recorded in the audit log as RATE_LIMITS_CHANGED. Counters are kept in memory and reset when the API restarts. SSH has no connection rate limit, because the deploy opens many SSH sessions in a row; fail2ban handles SSH password guessing.

How to checkTest against UAT, not production. The sign-in test uses made-up emails, so no real account is locked.
# Sign-in limit: the first 10 attempts answer 401 (wrong password), then 429
U=http://2.24.60.124:8088
J=$(mktemp); curl -s -c $J $U/api/v1/auth/csrf >/dev/null
T=$(awk '$6=="XSRF-TOKEN"{print $7}' $J)
for i in $(seq 1 12); do
  curl -s -o /dev/null -w "%{http_code} " -b $J -H "X-XSRF-TOKEN: $T" -H "Content-Type: application/json" \
    -d "{\"email\":\"ratetest$i@example.invalid\",\"password\":\"x\"}" $U/api/v1/auth/login
done; echo
# expect: 401 401 401 401 401 401 401 401 401 401 429 429

# The 429 answer says how long to wait
curl -s -D - -o /dev/null -b $J -H "X-XSRF-TOKEN: $T" -H "Content-Type: application/json" \
  -d '{"email":"ratetest@example.invalid","password":"x"}' $U/api/v1/auth/login | grep -i retry-after

# General limit: 650 quick calls, the last ~50 answer 429 (wait a minute before using UAT again)
seq 1 650 | xargs -P 20 -I{} curl -s -o /dev/null -w "%{http_code}\n" $U/api/v1/auth/csrf | sort | uniq -c
# expect roughly:  600 200   and   50 429

# A fake X-Forwarded-For does not reset the counter (still 429 inside the same minute)
curl -s -o /dev/null -w "%{http_code}\n" -H "X-Forwarded-For: 1.2.3.4" $U/api/v1/auth/csrf

The limiter also has its own automated test (RateLimitFilterTest), which runs with the backend tests: cd backend && ./gradlew :invoice-api:test.

HTTPS

Production is served only over HTTPS by Caddy, which obtains and renews the Let's Encrypt certificate automatically.

  • HTTP on port 80 redirects to HTTPS. Active
  • HSTS (Strict-Transport-Security: max-age=31536000; includeSubDomains) tells browsers to use HTTPS only, for one year. Added
  • On production the session cookie is Secure, so it is never sent over plain HTTP. Signing in therefore only works at the HTTPS address. Active
How to check
curl -sI http://erp.bipgulf.com | head -3            # expect 308 redirect to https://
curl -sI https://erp.bipgulf.com | grep -i strict      # expect the HSTS header
echo | openssl s_client -connect erp.bipgulf.com:443 -servername erp.bipgulf.com 2>/dev/null | openssl x509 -noout -issuer -dates
# expect issuer Let's Encrypt and a notAfter date in the future

For a full grade, enter erp.bipgulf.com at ssllabs.com/ssltest (expect A or A+).

Sign-in & sessions

PasswordsStored only as BCrypt hashes (cost 12). Nobody, including admins, can read a password.
Session cookieA signed token in a cookie marked HttpOnly (page scripts can't read it), Secure and SameSite=Strict. It expires after 12 hours.
Sign-outRevokes the token on the server, so a copied cookie stops working.
Disabled usersChecked on every request. Disabling someone signs them out immediately.
Error messages"Email or password is incorrect" in all cases, so the login page doesn't reveal which emails exist.
Lockout5 wrong passwords lock the account for 15 minutes. Failed sign-ins are recorded in the audit log.
How to checkIn the browser, open DevTools → Application → Cookies after signing in. fatoora_session must show HttpOnly ✓, Secure ✓ (production), SameSite Strict. From a terminal:
# Without signing in, data is refused
curl -s -o /dev/null -w "%{http_code}\n" https://erp.bipgulf.com/api/v1/invoices          # expect 401
# A forged token is refused
curl -s -o /dev/null -w "%{http_code}\n" -b "fatoora_session=forged.token.value" https://erp.bipgulf.com/api/v1/invoices   # expect 401

CSRF protection

Every change (create, edit, delete) must carry the X-XSRF-TOKEN header matching the XSRF-TOKEN cookie. Another website can't read that cookie, so it can't make your browser submit changes. SameSite=Strict on the session cookie adds a second barrier.

How to checkA write without the token is refused even when signed in. The automated check below tests this.
# With a valid session cookie in $J but no token header: expect 403
curl -s -o /dev/null -w "%{http_code}\n" -b $J -H "Content-Type: application/json" \
  -X POST http://2.24.60.124:8088/api/v1/customers -d '{"nameEn":"CSRF test"}'

Roles & permissions

  • Roles: Admin › Accountant › Viewer. Each includes the rights of the roles below it. Viewers can only read.
  • Per-feature access: for each user an admin ticks the features and actions (view, create, update, delete) they may use, and chooses whether they see all data or only their own.
  • Branch logins: limited to invoices, quotations, agreements, their own cash book and the shared customer and product lists. Every record they get back is filtered to what that login created.
  • Provider (operator) role: a company admin can't create provider accounts or switch the ZATCA environment.
  • Unknown or foreign records answer 404 without detail, so ids can't be probed.
How to checkSign in as a Viewer and try to add a product, open Settings → Users or change bank details. Each is refused. The automated check creates temporary Viewer and Branch users and tests all of this, then disables them.

Injection & input validation

  • All database queries use bound parameters. Report grouping and document types are matched against fixed lists, never pasted into SQL.
  • Names and text are escaped in PDFs and pages, so <script> typed into a field stays plain text.
  • Validation rejects negative quantities and prices, documents without lines, malformed VAT numbers and malformed JSON (answering 400, never 500).
  • Uploads check the file type. A logo must be an image.
  • Public invoice links in customer reminders carry an HMAC-SHA256 token, so they can't be guessed from an invoice number.
How to checkCovered by sections 5 and 6 of the automated check (SQL injection in search, timing-based injection, HTML in names, invalid values).

Data & secrets

  • ZATCA EGS private keys and CSID secrets are encrypted in the database with AES-256-GCM, using a master key that lives only in the server's env file.
  • Secrets (database password, session signing key, master key, admin password) are kept in deploy/clients/*.env. These files are not in git, and on the server they are readable only by root (chmod 600).
  • UAT and production use separate databases (bip_uat, bip_prod), with separate logins and secrets.
How to check
# On the server: expect -rw------- root root
ls -l /opt/bip-erp/deploy/clients/
# On your computer: expect no output (env files are not tracked)
git ls-files deploy/clients | grep -v example

Backups & updates

  • Nightly backups of both databases at 02:30 server time, kept for 14 days, in /opt/bip-erp/deploy/backups. Active
  • Automatic security updates for Ubuntu (unattended-upgrades). Active
  • Off-server copy of the backups (to another machine or cloud storage) is not set up yet. Recommended
How to check
ls -lh /opt/bip-erp/deploy/backups | tail -6       # expect today's bip_uat and bip_prod dumps
systemctl is-active unattended-upgrades            # expect active
cat /etc/apt/apt.conf.d/20auto-upgrades            # expect both values "1"

Audit log

Sign-ins, failed sign-ins and changes to records are recorded with the user and time. Admins see them under Settings → Audit log. Repeated LOGIN_FAILED entries for one email suggest someone is guessing that account's password.

Automated security check

deploy/security-check.sh runs about 40 non-destructive checks at a low request rate. It covers sign-in, CSRF, roles, record ownership, injection, validation, cookies, headers and sign-out. It creates a few clearly named test records and two temporary users, then removes or disables them. Run it against UAT.

# From the erp folder on your computer (Git Bash), with UAT admin credentials
BASE=http://2.24.60.124:8088 EMAIL='admin email' PASSWORD='admin password' bash deploy/security-check.sh
# expect the last line:  == NN passed, 0 failed, N notes

On plain-HTTP UAT, "session cookie not Secure" appears as a note. That is expected there; production uses HTTPS with Secure cookies.
